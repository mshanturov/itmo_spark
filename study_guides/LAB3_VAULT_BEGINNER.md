# ЛР3 — Секреты через Ansible Vault (очень подробное объяснение)

> Продолжение ЛР2 в `classic_developer_ml_cicle`

---

## 0. Главная идея ЛР3

В ЛР2 сервис уже работал с Redis, но секреты могли легко оказаться в открытом виде.

ЛР3 делает важный шаг к безопасности:
- секреты шифруются в Vault,
- при запуске контейнеров расшифровываются,
- сервисы получают секреты из файлов/переменных,
- plaintext-файлы с секретами в репозиторий не попадают.

---

## 1. Теория простыми словами

### Почему нельзя хранить секреты в коде
Если секрет в git:
- его видит любой, у кого есть доступ к репо;
- сложно ротация;
- высокий риск утечки.

### Что делает Vault
Vault = «сейф»:
- кладёшь секреты в зашифрованном виде,
- даёшь пароль доступа,
- при запуске извлекаешь безопасно.

В этой лабе используется **Ansible Vault**.

---

## 2. Как построен поток работы

1. На build-этапе `vault-init` создаёт зашифрованный файл `infra_secrets.vault`.
2. На run-этапе `vault-init` расшифровывает его и кладёт секреты в volume `/vault/output`.
3. `redis`, `web`, `kafka-consumer` читают файлы вида:
   - `/vault-secrets/redis_password`
   - `/vault-secrets/redis_host`
   - и т.д.
4. Сервис собирает URL подключения динамически.

---

## 3. Разбор ключевых файлов

## `docker/vault/init_vault.sh`

Скрипт формирует временный YAML и шифрует его:
```sh
ansible-vault encrypt /tmp/infra_secrets.yml \
  --output /vault/store/infra_secrets.vault \
  --vault-password-file /tmp/.vault_pass
```

После этого plaintext удаляется:
```sh
rm -f /tmp/infra_secrets.yml /tmp/.vault_pass
```

Очень важная практика: временные секретные артефакты не оставлять на диске.

## `docker/vault/export_secrets.sh`

Расшифровка и экспорт:
- читает пароль `ANSIBLE_VAULT_PASSWORD`,
- делает `ansible-vault view`,
- Python-блоком раскладывает по файлам в volume.

Плюс такого подхода:
- downstream сервисам не нужен ansible-vault,
- они просто читают файлы.

## `src/prediction_store.py`

Здесь логика чтения секрета:
```python
def _get_secret_value(env_name: str, file_env_name: str, required: bool = True) -> str:
    ...
```

Порядок:
1. если есть `*_FILE` — читаем файл,
2. иначе берём `ENV`,
3. если ничего нет и required=True — `StoreError`.

Это гибко: и для Docker, и для локального режима.

`resolve_redis_url()` собирает строку подключения из компонентов.

---

## 4. Что поменялось в docker-compose

Появляется сервис `vault-init`, и сервисы получают volume с секретами:
```yaml
volumes:
  - vault-secrets:/vault-secrets:ro
```

Redis стартует с `--requirepass`, пароль читается из файла.

Это значит: даже локальный запуск становится ближе к production-паттерну.

---

## 5. Как это разрабатывалось бы по шагам

1. Вынести чтение секретов в utility-слой.
2. Подготовить контейнер, который умеет encrypt/decrypt.
3. Добавить общий volume для секретов.
4. Изменить все сервисы, чтобы они читали `*_FILE`.
5. Добавить тесты secret-resolution.
6. Обновить CI/CD, чтобы передавались нужные credentials.

---

## 6. Что проверять руками

1. `vault-init` завершился успешно.
2. В volume появились файлы `redis_host`, `redis_password` и т.д.
3. Redis принимает пароль из файла.
4. API умеет читать/писать в Redis.
5. Тесты не требуют plaintext секретов в репозитории.

---

## 7. Почему это важно для следующих лаб

- В ЛР4 этот же механизм используется для Kafka-секретов.
- В ЛР8 паттерн переносится в k8s (через секреты/конфиги).

То есть ЛР3 — ключ к безопасной инфраструктуре дальше.

---

## 8. Типовые ошибки

- ❌ Хранить реальные пароли в `.env` и коммитить.
- ❌ Не удалять временные plaintext-файлы.
- ❌ Чтение секрета только из ENV без fallback на файл.

У тебя это закрыто корректно.

## 9. Короткий текст для защиты

«В ЛР3 я вынес работу с секретами в Ansible Vault: секреты шифруются в отдельном контейнере, при старте окружения расшифровываются и экспортируются в shared volume, а сервис модели и Redis читают их через `*_FILE` переменные. В результате чувствительные данные не хранятся в коде и локальных конфигурациях в открытом виде.»
